# 主题化改造 · 取舍记录

> 记录本次改造中每一个**有争议的、看起来可以那样做的**决定，以及为什么最后没那样做。
> 每条都带依据（实测数字 / 规范条款 / 结构性理由）。
> 实现细节见 [THEMING.md](./THEMING.md)，视觉规范见 [UI-GLASS-GUIDE.md](./UI-GLASS-GUIDE.md)。

## D1 · 浅底不用 aurora（极光）效果

**决策**：glass 首页的彩色氛围用**三层静态径向渐变**（`--bg-mesh`），不用极光式的流动色带 / 噪声 / 多层叠加。

```css
--bg-mesh:
  radial-gradient(60% 50% at 12% 8%, rgba(96, 165, 250, .28), transparent 70%),
  radial-gradient(50% 45% at 88% 4%, rgba(129, 140, 248, .24), transparent 70%),
  radial-gradient(45% 40% at 70% 92%, rgba(34, 211, 238, .18), transparent 70%);
```

**依据**：

1. **对比度必须可预算**。极光效果通常靠多层低透明度色带叠加 + 混合模式，最终某一点的亮度取决于层数与混合结果 —— 是**算得出来但改一次要重算一次**的。三层径向渐变收边到 `transparent 70%`，几何是确定的，`check-contrast.mjs` 能对它做真实几何采样（`meshAt` / `worstBackdropFor`）。
2. **LCP**。极光常用 `<canvas>` 或 WebGL，会引入 JS 执行与首帧绘制，直接把 LCP 从文本推到 canvas。纯 CSS 渐变不产生网络请求、无解码开销。
3. **视觉方向**。目标是「蓝白玻璃、干净通透」，极光是「深色科技风」的语言。浅底上做极光会显得脏 —— 浅底没有足够暗的底子去衬托发光色带。
4. **性能**。多层渐变 + `blend-mode` 在大屏上是一次不小的首帧光栅化成本。

**次选方案**（若将来要更强的氛围感）：在**深色**主题（D8 提及的第三套主题）上做极光。深底才是它成立的语境。

## D2 · 商家后台不用模糊

**决策**：`/admin/*` 全站不使用 `backdrop-filter`。后台的层次感靠**实色分层 + 细边框**建立（`--surface-1/2/3` → 现名 `--surface-solid` / `--bg-card` / `--admin-bg`）。

**依据**：

1. **它是收钱工具，不是展示页**。商家每天在上面看订单、核金额、对账。任何让数字「随背光变化」的视觉效果都是在增加出错概率。
2. **数据密集界面的对比度无法用玻璃保证**。表格有斑马纹、hover 态、选中态、禁用态，再乘以玻璃的半透明底 —— 组合数爆炸，无法逐个验收。实色底让每一条组合都是固定值。
3. **长时间盯屏**。半透明表面会让整个界面「发飘」，需要眼睛持续重新对焦。
4. **性能**。后台页面的 DOM 结构比 C 端复杂得多（表格行数不设限），大面积 `backdrop-filter` 在滚动时是明确的掉帧源。

**具体做法**：`glass-app.css` 里通过**在 `.dashboard` 上覆盖令牌**实现，而不是逐个组件写规则：

```css
.dashboard {
  --surface-glass:        var(--surface-solid);
  --surface-glass-strong: var(--surface-solid);
  --surface-glass-quiet:  var(--surface-solid);
  --glass-blur:           none;
}
```

这样后台子树里的 `.glass` 类全部自动变成实色，**组件本身一行都不用改**。

**已知代价**：后台在 glass 主题下与 classic 主题的差异因此很小（主要是配色与圆角）。这是有意的 —— 后台不做主题化的视觉实验。

## D3 · 每页玻璃 ≤ 5 个

**决策**：同一视口内可见的玻璃容器不超过 5 个。首页当前 5/5。

**依据**：

1. **实测上限**。5 个是滚动时仍保持 60fps 的实测边界（见验收报告滚动性能：帧间隔 p50 16.7ms、最长帧 16.8ms、长帧占比 0.0%）。
2. **视觉上限**。超过 5 个之后，人眼不再把它们读作「几块浮起的面板」，而是一堆半透明方块 —— 层级感反而丢失。玻璃的视觉效果依赖**对比**（有实底才显得玻璃通透）。
3. **可验收**。一个具体数字才能被检查。写「适量使用」等于没写。

**计数口径**：视口内**可见**的玻璃容器。滚出视口的不算，`display: none` 的不算，移动端抽屉收起时不算。

**超预算时怎么办**：换成实色表面（`--surface-solid`），保留圆角与阴影 —— 视觉上仍是「一块面板」，只是不通透。

## D4 · `-webkit-backdrop-filter` 里硬编码数值

**决策**：前缀属性写字面量，标准属性用变量。

```css
.glass {
  -webkit-backdrop-filter: saturate(180%) blur(18px);
  backdrop-filter: var(--glass-blur);
}
```

**背景**：Safari 长期只认带前缀的 `-webkit-backdrop-filter`。而部分引擎在解析前缀属性时**不解析 `var()`** —— 整条声明被丢弃，表现为「Safari 上完全没有模糊，其余浏览器正常」。

**为什么可以安全地硬编码**：这些类**只在 glass 主题下存在**（选择器是 `:root[data-theme="glass"] .glass`）。classic 下这些类不存在，因此不存在「前缀属性与标准属性取值不一致」的窗口 —— 那才是硬编码真正危险的地方。

**护栏**：`check-tokens.mjs` 有一条断言解析 `glass.css`，比对 `-webkit-backdrop-filter` 的字面量与 `--glass-blur` 的取值是否一致。**改模糊强度必须同时改两处**，否则构建检查会失败。

## D5 · `:root` 与 `:root[data-theme="classic"]` 写在同一组选择器里

**决策**：

```css
:root,
:root[data-theme="classic"] {
  /* classic 的全部语义值 */
}
```

**依据**：

1. **`:root` 本身必须是可用的兜底**。首访用户（无 localStorage）、`localStorage` 不可用（隐私模式）、`?theme=evil`（非法值）—— 这些情况下 `index.html` 的内联脚本**刻意不写 `data-theme`**。如果 classic 的值只挂在 `:root[data-theme="classic"]` 上，这些用户会看到一个**没有任何令牌值**的页面。
2. **`color-scheme` 必须写在这里**。它需要覆盖首访场景。
3. **避免特异性陷阱**。若把 classic 写成独立的 `:root[data-theme="classic"]` 块放在 `:root` 之后，两者特异性不同（0,2,0 vs 0,1,0），后续任何针对 `:root` 的降级块都会输给 classic —— 这类问题只在特定主题下复现，极难排查。

**代价**：选择器看起来冗余。已在 `tokens.semantic.css` 顶部用注释说明原因。

## D6 · glass 首页用静态 `import`，不用异步 chunk

**决策**：`WelcomeView.vue` 里 `import GlassHome from '@/components/home/GlassHome.vue'` —— 静态导入，不拆 chunk。

**背景**：最初为了避免 classic 用户下载 glass 的代码，改成了 `defineAsyncComponent`。

**依据**：实测 Lighthouse 移动端（4× CPU 降速）显示**异步版本 LCP 恶化 26%**。原因很直接：glass 的 LCP 元素是 Hero **文本**，而文本要等 chunk 下载 + 解析 + 执行完才能绘制。拆包省下的字节数远小于多一次往返的代价。

**旁证**：在异步版本里，glass 的 LCP 元素**曾是** `<p class="gh-hero__desc">`（文本）；改回同步后 LCP 元素变成了启动闪屏图 —— 恰恰说明它不再等 chunk 了。

**结论**：这是被测量推翻的假设，已回退。

## D7 · 光斑不做漂移动画

**决策**：`body::before` 上的光斑是**静态**的，不做缓慢漂移。

**依据**：

1. **与对比度验收直接冲突**。Hero 标题就压在光斑上。光斑漂移意味着标题底色的亮度随时间变化，对比度**没有固定值** —— 而「正文对比度 ≥ 4.5:1」是硬性验收项，不是一个可以「大部分时候满足」的指标。
2. **持续合成开销**。漂移动画意味着这个 80px 模糊的大图层永远不能进入静止状态。
3. **收益接近零**。静态光斑已经提供了足够的氛围；漂移在浅底 + 低透明度下几乎看不出来。

**推论（写给后来者）**：任何新增的、压在文字下面的装饰层都必须**静态**。要动效就动别的东西 —— `transform` / `opacity`，且不改变文字底色。

## D8 · 不做「跟随系统深色模式」

**决策**：`prefers-color-scheme` **不参与**主题选择。系统开了深色模式，本应用仍是浅色。

**依据**：

1. **商家后台不该某天打开变个样**。它是工作工具，不是内容消费应用。用户的系统偏好不应该在无人告知的情况下改变他们每天面对的工作界面。
2. **两套主题 ≠ 深浅两种模式**。classic 与 glass 是**同一明度方向**的两套风格（都是浅色），不是 light/dark。把它们当作深浅模式是范畴错误。
3. **第一优先级是 classic 零回归**。跟随系统会让一部分用户看到与改造前不同的界面 —— 直接违反约束。

**测试覆盖**：`theme-defaults.spec.mjs` 有一条用例专门验证「系统深色模式下仍是浅色主题，且 `color-scheme: light` 生效」。

**未来**：若要出第三套主题，**深色是一个合理的候选**（见 D1 的次选方案）—— 但应当是用户**显式选择**的，而不是自动跟随的。

## D9 · `?theme=` 是只读覆盖，永不写入 localStorage

**决策**：URL 查询参数优先级最高，但**不落盘**。

**依据**：`?theme=glass` 的用途是 QA 验证与分享链接。如果它写存储，那么任何人点开一条带参数的链接，自己的长期偏好就被永久改掉了 —— 而且他们不知道。这类 bug 极其隐蔽：用户只会觉得「我的主题设置偶尔会自己变」。

**实现**：`useTheme.js` 的 `setTheme()` 里 `if (!queryOverride) writeStored(theme)`。

**测试覆盖**：`theme-defaults.spec.mjs` 验证「带 `?theme=` 访问 → 存储原值不变」。

**相关**：`isThemeForced()` 暴露给切换器，用于提示用户「本次会话的主题被 URL 固定」。

## D10 · `resetTheme()` 不写存储，而不是写默认值

**决策**：`resetTheme()` 清掉存储项后**不回写**默认值。

**背景**：最初实现是 `removeItem()` 之后调 `setTheme(默认值)` —— 看起来等价，其实不是。

**依据**：`setTheme()` 会因为「主题确实变了」而把默认值写回存储，于是存储里留下 `'classic'`。「清掉偏好」这个语义就丢了 —— 用户表达的是「我放弃之前的选择」，而不是「我选择 classic」。

**后果差异**：将来默认主题若改变（比如默认改成 glass），**没有存储项**的用户会跟着变；存储里写着 `'classic'` 的用户不会。前者才是「恢复默认」应有的行为。

**教训**：`resetTheme` 与 `setTheme(DEFAULT)` 是两个不同的动作，必须分别实现。切换器里给的是前者。

## D11 · 存储不可用时用内存兜底，而不是单纯 try/catch

**决策**：`storage.js` 每个方法都包 try/catch，失败时退到模块级 `Map` 内存缓存，并**只打一次** `console.warn`。

**背景**：这是一个**既存缺陷的修复**。原实现直接调 `localStorage` 且无保护。路由导航守卫每次跳转都读 token —— 于是只要 `localStorage` 抛错（Safari 无痕、禁用 Cookie、沙箱 iframe、企业策略），守卫就抛异常、导航被中止、**整个应用白屏**。

**为什么不是单纯吞掉异常**：吞掉之后 `set()` 后再 `get()` 会拿到 `null`，登录态在同一次会话内就丢了 —— 用户会看到「刚登录完又被踢回登录页」，比白屏更费解。内存兜底保证**本次会话内读写自洽**，只是刷新后不保留。

**为什么只 warn 一次**：每次读写都打就成了刷屏，反而掩盖真正的问题。

**验证口径**：这个缺陷**改造前的产物同样存在**（实测两者在隐私模式下都渲染空白）—— 不是本次引入的，但既然碰到了就修掉。属于「顺手修」而非「顺手改」。

## D12 · `!important` 净增 8 条

**决策**：接受净增 8 条 `!important`，不追求归零。

**依据**（逐条分类）：

- **7 条**在 `glass-app.css`，用于覆盖 Element Plus **本身带 `!important`** 的声明（`.el-input__wrapper` 的背景/边框、`.el-table th` 的背景等）。同源同层下，非 `!important` 声明**打不过** `!important`，没有别的办法。
- **1 条**在 `fx.css` 的 `prefers-contrast: more` 块里，用于确保用户的无障碍偏好**一定能生效**。这是少数几个「比覆盖优先级更重要」的场景。

**全部都在主题专属文件里**，classic 主题下一行都不命中 —— 所以不构成 classic 回归风险。

**若要归零**：需重构 `element-bridge.css` 去掉它自己的 `!important`（同样是历史遗留）。风险大于收益，未做。

## D13 · `prefers-contrast` 块的优先级选择器

**决策**：

```css
@media (prefers-contrast: more) {
  :root[data-theme='glass'] { /* 提高不透明度与对比度 */ }
  :root[data-theme='classic'] { /* ... */ }
}
```

**背景**：最初写的是 `:root`。**这是一个真实的 bug**：`:root[data-theme='glass']` 的特异性是 (0,2,0)，高于 `:root` 的 (0,1,0) —— 于是对比度提升在 glass 主题下**完全不生效**，而且不报任何错。只在开启 `prefers-contrast` 的用户那里复现。

**教训**：任何写在 `fx.css` 里的降级/无障碍块，只要目标是「覆盖某个主题的值」，选择器就必须带上主题限定符，**特异性要匹配**。

**测试覆盖**：`fx.spec.mjs` 的 `emulateContrast`。注意 Playwright 的 `page.emulateMedia({ contrast: 'more' })` **被静默忽略**，必须走 CDP `Emulation.setEmulatedMedia` —— 最初用了前者，测试**因为错误的原因通过**了。非 Chromium 引擎下该用例会跳过并给出明确提示（CDP 是 Chromium 专有）。

## D14 · 状态语义用三元组（填充 / tint / ink）

**决策**：每个状态色定义三个值，而不是一个。

```css
--c-mint-400: #A8D8B9;   /* 填充 */
--c-mint-50:  #EDF6F0;   /* 浅底 (tint) */
--c-mint-700: #3E6B4E;   /* 文字 (ink)  6.14:1 */
```

**背景**：原体系每个状态只有一个浅色值，被**同时当作填充和文字**使用。结果「订单金额」「拒绝原因」这类关键文字只有 1.3–1.9:1 —— 完全读不了。

**依据**：一个颜色无法同时满足「作为填充要浅」和「作为文字要深」两个相反需求。这不是调色问题，是结构问题。

**代价**：令牌数量增加。但这是必要的 —— 用单个值硬撑的结果就是关键信息不可读。

**另注**：`--sakura` 这个历史别名在改造中被**修正**（原指向 `#F9E0A0`，1.30:1，导致「订单总价看不见」），现在指向 `--color-primary-ink`。这是修正而非改名。

## D15 · Lighthouse 绝对分值不达标 → 单独立项，不塞进本次改造

**决策**：记录为遗留问题，不在本次主题化改造中处理。

**实测**：classic 8.33s / glass 8.35s（+0.02），TBT 1.04s / 1.03s（−0.01），CLS 0.0000 / 0.0000。Performance 分值 35。

**为什么不是本次议题**：

1. **两套主题持平** —— LCP 差异 +0.02s、TBT 差异 −0.01s，都在噪声范围内。这不是主题化引入的。
2. **根因是既存的包体积**：1MB JS 单包 + ~400KB CSS（EP 占绝大部分）。改造前后同一量级。
3. **修它要动代码分割与 EP 按需引入**，会大范围影响加载路径 —— 与本轮「classic 零回归」的第一优先级直接冲突。混在一起做，一旦出现回归就分不清是主题化还是分割引入的。

**改善路径（建议单独立项）**：① 主 JS 做 `manualChunks`；② Element Plus 改按需引入；③ 把首屏所需的最小样式内联，缩短启动闪屏的停留时间。

## D16 · 没有加 `contain: paint` / `isolation: isolate`

**决策**：规格里提到这两项，但**没有实施**。

**依据**：它们是为「减少重绘范围」而存在的优化手段，前提是**确实存在大范围重绘**。

**实测结果否定了这个前提**：

| 假设 | 验证方式 | 结果 |
|---|---|---|
| `blur(80px)` 光斑是 TBT 主因 | 移除后重测 | TBT 932 → **938 ms**（无变化）|
| 5 个 `backdrop-filter` 层是 TBT 主因 | 全部移除后重测 | TBT 938 → **938 ms**（无变化）|

glass 比 classic 多出的约 200–400ms 主线程开销，来源是**页面本身更大**（DOM 约 5 倍 + 自带 CSS），不是特效。

**为什么坚持不加**：没有数据支撑的调优就是 cargo cult。而且 `contain: paint` 会**裁掉 `box-shadow`**、改变绝对定位子元素的包含块 —— 是有副作用的。

**如果将来真的需要**：先测出重绘范围确实过大，再加，并验证副作用。

## D17 · glass 的 `--border-input` 是唯一为达标而加深的描边

**决策**：glass 下 `--border-input: #7E8FA9`，而不是设计给定的 `rgba(37, 99, 235, .14)`。

**依据**：给定的 `rgba(37,99,235,.14)` 合成到白底只有 **1.22:1** —— 输入框边界几乎不可辨，属于 WCAG 1.4.11「非文本对比度」里的「控件形状无法识别」。`#7E8FA9` 对纯白底 3.29:1、对后台浅底 3.06:1，均过 3:1 线。

**范围控制**：这是 glass 主题下**唯一**一处为了达标而明显加深的描边，其余边框保持设计给的浅色。已在 `tokens.semantic.css` 就地注释说明。

## D18 · `--radius-btn` 桥接到 Element Plus

**决策**：在 `element-bridge.css` 增加 `.el-button { border-radius: var(--radius-btn) }`。

**背景**：EP 的按钮圆角来自编译期 SCSS 变量（`$button-border-radius: 9999px`），运行时改不动。glass 主题需要「方圆角」而非「胶囊」，否则按钮与周围 `--r-12` 的输入框/卡片不协调。

**为什么不算 classic 回归**：这条规则对 classic 也生效，但在 classic 下 `--radius-btn` 的值恰好等于编译期字面量 `9999px` —— 渲染结果逐像素不变。已由视觉基线验证（27/29 零差异，另 2 张的差异仅来自首页主题入口）。

**推论**：主题**不能**改变 EP 组件的尺寸与内边距（那些也是编译期的）。要改就得改编译期，那会同时影响所有主题 —— 这一点已写进 [THEMING.md](./THEMING.md) §5.2。

## D19 · classic 的令牌值从「颜色频率倒推」，而不是重新设计

**决策**：L1/L2 的所有 classic 值都是从改造前产物里**倒推**出来的精确快照，不是重新挑的颜色。

**依据**：第一优先级是「classic 视觉逐像素不变」。任何「顺手优化一下这个灰」都会变成回归。

**验证**：4 种层叠条件下各 262 项有效值、共 1048 项比对，**差异 0**。

**代价**：有几个值看起来「不整齐」（比如 `#FDFBF7` 与 `#F9F8F6` 只差一点）。这是原样保留的结果，不是失误。`tokens.primitives.css` 顶部已注明「本文件的值 = classic 线上渲染的精确快照，任何数值改动都会造成像素回归」。

## D20 · 主题切换事件只派发 DOM 事件，不直接上报

**决策**：`theme:switch` 是一个 `CustomEvent`，`useTheme.js` 里**不调用任何上报接口**。

**依据**：项目**目前没有任何分析/埋点方案**（已确认：无 gtag / 百度统计 / Sentry）。而 `api/log.js` 那个 `/logs` 端点写的是**商家操作日志** —— 往里塞主题切换会污染商家的操作记录，是数据污染。

**做法**：只派发事件。将来接入分析工具时，在入口处订阅即可，**不必回头改这个文件**：

```js
window.addEventListener('theme:switch', (e) => {
  analytics.track('theme_switch', e.detail)   // { from, to }
})
```

**兜底**：`CustomEvent` 不被支持时静默 —— 埋点是增强，不该影响切换本身。

## 附：被否决的方案

| 方案 | 否决理由 |
|---|---|
| 两套平行的样式表，按主题切换 `<link>` | 违反硬约束；且切换时有闪烁窗口，classic 回归风险无法控制 |
| 在组件里写 `if (theme === 'glass')` 分支 | 违反硬约束；逻辑散落，加第三套主题要改遍所有组件 |
| 用 `<canvas>` / WebGL 做背景 | 引入 JS 执行与首帧绘制，LCP 元素不再是文本 |
| 把主题色值抄进 `THEME_CONFIG` 供预览用 | 会在令牌调整后**安静地过期**。改为 `readThemeTokens()` 临时切换 + 读 computed style（同一 JS 任务内完成，不会闪） |
| 切换器用截图做预览 | 截图会在主题演进后过期，且需要额外的图片资源 |
| 用 UA 嗅探判断浏览器降级 | 规格明确禁止；改用 `@supports` 真实特性检测 |
| 低端设备**禁用**玻璃效果 | 启发式（`hardwareConcurrency ≤ 4` / `deviceMemory ≤ 4`）只做「**减负**」不做「禁用」—— 判定不准时会误伤，减负错了只是效果淡一点，禁用错了是功能缺失 |
| 主题切换时给页面加自定义交叉淡入动画 | 手写动画容易写出「白闪」。不支持 View Transitions 的浏览器**直接瞬时切换**，不做任何补偿动画 |
