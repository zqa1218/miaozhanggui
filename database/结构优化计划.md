# 喵掌柜 数据库结构优化 + 微信小程序顾客功能 —— 设计方案

> 版本：v1（2026-09-03）
> 依据：全后端源码（13 模块 / 36 迁移 / 19 张线上表）+ 线上库实况核对。
> 总原则：**只新增表/新增可空列/新增索引/新增接口；不删列、不收缩 ENUM、不改既有接口契约 → 不影响当前网站功能。**

---

## 一、现状关键结论（为何必须这样做）

| 方面 | 现状事实 | 推论 |
|---|---|---|
| **Schema 漂移** | 线上库与 `database/migrations/` 不一致：`orders.user_id`、`character_image`、`reference_images`、`order_no` 计数表、`is_admin`、更宽的 `status` ENUM（含 `定金待确认/未结清`）由**裸 SQL 直接加在库上**，未纳入迁移；迁移 `032` 未记录却已有 `extra_items` 列。 | 新迁移必须**对线上实际列做 `hasColumn/hasTable` 幂等判断**，不能假设迁移目录即事实。 |
| **并发** | 防超卖靠 `slot_bookings` 唯一键 `uq_slot_interval(m_id,studio_id,booking_date,start_time,end_time)` + `SELECT…FOR UPDATE`（`timeCollisionEngine.js`）。V2 下单时不写 slot 行，只有付定金（`payDeposit`）才插入 `pre_lock` 行 → 同一时段两笔"待支付"可并存，先付先得。 | 并发结论正确但需补：幂等防重、Redis 锁、超时/僵尸 `pre_lock` 清理。 |
| **Redis** | 客户端存在（`src/shared/redis/client.js`）但**全站零使用**；限流器是**进程内存 Map**，PM2 cluster 多实例下各自计数。**生产 Redis 当前不可达**（6379 拒绝连接）。 | 引入 Redis 必须带**内存降级**，Redis 挂了功能照常。 |
| **图片** | 存本地 `uploads/{covers,details,qrcodes,refunds,avatars,general,order_refs,styles}`，URL 是**相对路径** `/uploads/...`；`storage/index.js` 抽象是死代码（`upload.service.js` 硬编码 `require('./local')`）；`deleteFile` 从未被调用 → 换图产生**孤儿文件**；png→800px、其余→1200px jpg 单规格；有 `.svg/.txt` 混入、`webp` 存 jpg 扩展名错配。 | 图片优化改为**新增能力 + 出口 URL 拼公网前缀**，不改 DB 存量值。 |
| **小程序登录** | `auth.service.js` 的微信换码是**桩代码**（`return 'wx_' + code`），未真正请求微信；注释掉的 URL 是**网页版 OAuth**，无 `jscode2session`。`users.wx_open_id` 是网站开放平台 openid，与**小程序 openid 不是同一个值**。 | 小程序需**独立 openid 字段 + 新接口**，与现有网页登录并存。 |
| **按用户查单** | 后端 `clientAuth`/`optionalClientAuth`、JWT（`userId`）、`findByUser`（查 `orders.user_id`）已就绪；`orders.user_id` 线上已有列有索引（仅裸 SQL）。C 端 `getMyOrders` 目前要求 `mId`，匿名按 `user_device_id`。 | 只需把 `orders.user_id` 固化进迁移、补组合索引，小程序端新增用户域订单接口即可。 |
| **WebSocket** | 客户通道按 `deviceId` 订阅；商户按 `mId`。小程序账号用户换设备会丢失推送。 | 客户通道应额外支持按 `userId` 订阅。 |

## 二、实施铁律（保障"不影响原网站"）

1. **只增不删不改语义**：本次所有迁移 = 新增表 / 新增可空列 / 新增索引。绝不 DROP，绝不 `ALTER` 收缩 ENUM。
2. **幂等 guard**：每个加列/建表前 `await knex.schema.hasColumn / hasTable`（沿用现有 017/022/025 的风格）。
3. **以线上库为基线**：动手前先导出一份 `mysqldump` 完整备份；`deploy.sh` 中在 `knex migrate:latest` 之前**自动备份**一次（现在没有）。
4. **存量数据双兼容**：
   - 匿名老订单 `user_id = NULL`，继续靠 `user_device_id` 可查（不改）；
   - 小程序用户下单 `user_id` 写入，`user_device_id` 仍赋一个确定值（如 `mp_{openid 后 24 位}`）以兼容 NOT NULL 与旧归属校验。
5. **Redis 可降级**：所有 Redis 读写在 `catch` 后回退 MySQL / 内存，绝不因 Redis 宕机抛 5xx。
6. **图片相对路径存储值不变**：DB 里继续存 `/uploads/...`；需要公网/小程序展示时在**响应出口**用 `ASSET_BASE_URL` 拼绝对 URL，将来切 OSS/CDN 只改这一层。
7. **既有接口契约不动**：新能力全部走**新增路由**；改动的内部函数仅做行为等价重构（状态推进集中化）。
8. 部署顺序与 `deploy.sh` 一致（先 migrate 后 reload），确保新列先于引用它的代码生效。

## 三、数据库结构优化（新迁移 035~041）

### 3.1 顾客域 —— `users` 扩展（迁移 035）

保持现有 `wx_open_id / qq_open_id / union_id / nickname / avatar / phone` 不动，**追加**小程序所需列：

```sql
-- users 表 ADD（幂等）
ALTER TABLE users
  ADD COLUMN wx_mp_open_id       varchar(64)   NULL COMMENT '微信小程序openid(与网页openid不同)',
  ADD COLUMN wx_mp_session_key   varchar(128)  NULL COMMENT '小程序最近session_key(可空,仅用于解密)',
  ADD COLUMN last_login_at       datetime      NULL COMMENT '最近登录时间',
  ADD UNIQUE KEY uq_users_wx_mp (wx_mp_open_id);
```
> `phone` 已有普通索引，暂不强行改唯一（历史可能有脏数据）；如需手机号登录另立项。

### 3.2 顾客域 —— 新增表：登录渠道归一（迁移 036）

**`user_oauth_accounts`** —— 将来无论网页/公众号/小程序/QQ 登录都落一行，不再往 `users` 无限加 openid 列：

```sql
CREATE TABLE user_oauth_accounts (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id      BIGINT UNSIGNED NOT NULL COMMENT '关联 users.id',
  provider     ENUM('wechat_website','wechat_miniapp','qq') NOT NULL COMMENT '登录渠道',
  open_id      VARCHAR(128) NOT NULL COMMENT '该渠道 openid',
  union_id     VARCHAR(128) NULL COMMENT '开放平台 unionid(可空)',
  meta         JSON NULL COMMENT 'session_key 等原始信息',
  created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uq_oauth_provider_open (provider, open_id),
  KEY idx_oauth_user (user_id)
) COMMENT='顾客第三方登录账号';
```
> 新登录**同时写** `users.wx_mp_open_id`（兼容旧代码路径）与该表；后续再切换为读该表，切换前后功能一致。

### 3.3 顾客域 —— 让订单归属顾客（迁移 037）

把线上已有的裸 SQL 固化进迁移并补查询索引（幂等）：

```sql
ALTER TABLE orders
  ADD COLUMN user_id          BIGINT UNSIGNED NULL COMMENT '下单顾客 users.id',
  ADD COLUMN idempotency_key VARCHAR(64) NULL COMMENT '幂等键(小程序下单防重复)',
  ADD UNIQUE KEY uq_orders_idem (idempotency_key),
  ADD KEY idx_orders_user_status (user_id, status, created_at);
-- 已有 idx_user_id、idx_order_device(user_device_id,m_id) 保留
```
不动 `user_device_id`（NOT NULL 兼容匿名单 / Excel 导入单 `import_*`）。

### 3.4 订单时间线 & 支付流水 —— 新增表（迁移 038/039）

**`order_status_logs`（订单状态时间线）** —— 顾客端"查询订单状态/状态轨迹"与商户审计共用：

```sql
CREATE TABLE order_status_logs (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  order_id      BIGINT UNSIGNED NOT NULL COMMENT '关联 orders.id',
  order_no      VARCHAR(32)  NOT NULL COMMENT '订单号冗余',
  from_status   VARCHAR(32) NULL COMMENT '原状态',
  to_status     VARCHAR(32) NOT NULL COMMENT '新状态',
  actor_type    ENUM('system','merchant','customer') NOT NULL DEFAULT 'system' COMMENT '操作方',
  actor_m_id    VARCHAR(64) NULL COMMENT '操作商户(管理端)',
  actor_user_id BIGINT UNSIGNED NULL COMMENT '操作顾客',
  remark        VARCHAR(512) NULL COMMENT '备注',
  created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_osl_order (order_id, created_at),
  KEY idx_osl_no (order_no)
) COMMENT='订单状态流转记录';
```

**`order_payments`（每笔订单的定金/尾款支付记录）** —— 现在是"扫码转账→商家点确认"，无台账；顾客想确认"定金付了没、尾款结清没"：

```sql
CREATE TABLE order_payments (
  id               BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  order_id         BIGINT UNSIGNED NOT NULL COMMENT '关联 orders.id',
  order_no         VARCHAR(32) NOT NULL COMMENT '订单号冗余',
  type             ENUM('deposit','final') NOT NULL COMMENT '定金/尾款',
  amount           DECIMAL(10,2) NOT NULL COMMENT '金额',
  status           ENUM('unpaid','pending_confirm','paid') NOT NULL DEFAULT 'pending_confirm' COMMENT '状态',
  voucher_img_url  VARCHAR(512) NULL COMMENT '转账凭证图(可选)',
  remark           VARCHAR(512) NULL,
  confirmed_by     VARCHAR(64) NULL COMMENT '确认的 m_id',
  confirmed_at     DATETIME NULL,
  created_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_op_order (order_id, type)
) COMMENT='订单支付流水';
```
> 接入微信支付（小程序支付）后，在此表补 `channel / pay_transaction_id` 即可，属于追加。

### 3.5 并发 / 超时辅助列（迁移 040，建议）

```sql
ALTER TABLE slot_bookings
  ADD COLUMN lock_expires_at DATETIME NULL COMMENT 'pre_lock 过期时间;到点未转 hard_lock 可被清理',
  ADD KEY idx_slot_studio_date (studio_id, booking_date, lock_type);
```
僵尸 `pre_lock` 清理：新增定时任务，删除 `lock_type='pre_lock' AND lock_expires_at < NOW() AND 关联订单未进入已付/已确认` 的行。**注意**：释放一律 `DELETE`（`uq_slot_interval` 唯一键不允许同区间存活第二行），这样已释放时段才能被重新预定。

### 3.6 表 / 索引汇总

| 动作 | 对象 | 目的 |
|---|---|---|
| 加列 + 唯一键 | `users.wx_mp_open_id` 等 | 小程序登录 |
| 新表 | `user_oauth_accounts` | 登录渠道归一 |
| 加列 + 索引 | `orders.user_id`（固化）`idempotency_key` | 订单归属顾客 / 幂等 |
| 新表 | `order_status_logs` | 顾客查状态时间线、审计 |
| 新表 | `order_payments` | 支付台账 |
| 加列 + 索引 | `slot_bookings.lock_expires_at` 等 | pre_lock 超时释放 |
| **不动** | `merchants / studios / styles / schedule / notification / operation_logs / invitation_codes / order_no` 等 | 原功能零接触 |

## 四、Redis 与并发优化设计（全部可降级）

> 现状 Redis 未运行 → 按"Redis 可用 = 启用增强、不可用 = 自动回退"实现，**默认现状不变**。

| 场景 | Redis key / 用法 | DB 兜底 |
|---|---|---|
| **创建订单幂等**（双击/重试重复单） | `SETNX idem:createorder:{clientKey} PX 60000`，命中返回已有结果 | `orders.idempotency_key` 唯一键（权威） |
| **付定金临界区**（同单防并发提交） | `SETNX lock:order:{orderNo} PX 15000` | 现有 `FOR UPDATE` + `uq_slot_interval` |
| **时段抢占预检** | `SETNX lock:slot:{studioId}:{date}` 短锁，降低 DB 死锁 | DB 行锁 |
| **集群级限流** | `INCR` + `EXPIRE` `ratelimit:{deviceIp}:{op}` 滑动窗口 | 现内存 Map（保持默认限额） |
| **热点读缓存** | `cache:studio:{id}`、`cache:slots:{studioId}:{date}`(TTL 20–60s)、`cache:noti:{mId}` | 读 MySQL；写时 `delete` 失效 |
| **小程序会话** | `wxmp:{openid} → {session_key}`（短 TTL） | `users.wx_mp_session_key` 列 |
| **分布式锁封装** | `shared/redis/distLock.js`：成功返回回调结果，连不上返回空锁（= 不加锁走 DB） | — |

**并发规则建议（写入 `timeCollisionEngine` 备注）**：所有加锁统一按 `(studio_id, booking_date, start_time)` 排序获取，避免两笔反向加锁死锁（MySQL 1213），并对死锁做小退避重试。

## 五、图片传输与存储优化（新增能力，不影响现状）

1. **出口 URL 拼接**：`config` 增加 `ASSET_BASE_URL`（读 `.env`，如 `https://miazhanggui.xyz`），提供 `utils/assetUrl(path)`；小程序/需绝对地址的接口返回时拼前缀。**DB 存量相对值不动** → 未来上 CDN/OSS 只改配置 + 同步。
2. **修复死抽象**：`upload.service.js` 改为 `require('../../shared/storage')`（`index.js` 现即转发到 local），行为完全一致；预留 OSS 分支。
3. **删图治理**：改造 `studio/style/merchant/settings/refund` 的替换/删除点，在事务提交后调用现有但从未使用的 `deleteFile(urlPath)`（仅当 URL 属于本机 `/uploads/` 且无其他引用）；另加每日孤儿文件扫描（比对 DB 各 `*_url` / `*_img*` 列）。
4. **格式/尺寸**：上传时统一按真实编码修正扩展名（消除 `webp → .jpg` 错配，校验只作用于**新文件**）；新增缩略图变体（如列表用 400px `_thumb`），详情仍用 1200px 原图 → 小程序端省流量。
5. **文件合法性**：`multer` 过滤之外加 **magic bytes 校验**（避免 `.svg/.txt` 冒充，当前 uploads 已有此类文件），仅拦新上传。
6. **小程序域名**：在微信公众平台把 `https://miazhanggui.xyz` 加入小程序 **request / downloadFile 合法域名**；生产确认前端反代（宝塔/Nginx）对 `/uploads` 带正确 MIME 与缓存头。

## 六、微信小程序登录 + 下单 / 查单（接口设计，全部新增）

### 6.1 登录流程（快速注册 = 首次登录自动建号）

```
小程序 wx.login() → code
  POST /api/client/auth/mp-login  { code, nickname?, avatar? }
后端: https://api.weixin.qq.com/sns/jscode2session
      ?appid=WECHAT_MP_APPID&secret=WECHAT_MP_SECRET&js_code=code&grant_type=authorization_code
      返回 { openid, session_key, unionid? }
  1) 查 user_oauth_accounts(provider=wechat_miniapp, open_id=openid) → 存在则更新昵称/头像
  2) 未存在：按 unionid 尝试关联已有 users 行，否则 INSERT users（自动注册）
  3) 双写 users.wx_mp_open_id + user_oauth_accounts，签发现有 client JWT
响应 { token, user:{ id, nickname, avatar, phone }, isNew }
```
- `config` 增加 `wechat.mpAppId / mpSecret`（新 env `WECHAT_MP_APPID/SECRET`，**不动** `WECHAT_APPID`）。
- 手机号：小程序 `getPhoneNumber` 的 code → `wxa/business/getuserphonenumber` 写 `users.phone`（需商户认证；未认证则个人中心手动补，可选功能）。

### 6.2 小程序下单 / 查单接口

| 新接口 | 鉴权 | 行为 |
|---|---|---|
| `POST /api/client/order/create` | clientAuth | 复用 `createOrderV2` 全链路，`payload.userId = req.user.userId`，并带 `idempotency_key` |
| `GET /api/client/orders?mId=&status=&page=&size=` | clientAuth | **按 `user_id`** 拉"我的订单"，跨商户可不传 mId；走 `(user_id,status,created_at)` 索引 |
| `GET /api/client/orders/:orderNo` | clientAuth | 订单详情 + 归属校验（`user_id == req.user.userId` 或 `user_device_id` 匹配） |
| `GET /api/client/orders/:orderNo/timeline` | clientAuth | 读 `order_status_logs`，返回状态轨迹 |
| `GET /api/client/orders/:orderNo/payments` | clientAuth | 读 `order_payments`，返回定金/尾款支付状态 |
| `POST /api/client/order/{orderNo}/cancel` | clientAuth | 复用 request-cancel（归属校验同时兼容 user_id） |

**状态机**：不新建状态；把现有分散的"三字段推进"收敛为服务内一个 `transitionOrderStatus(trx, order, nextStatus, actor)`，内部先更新 `orders`、再 `insert order_status_logs`（等价重构）。顾客看到的"状态" = 现 `orders.status` 的语义映射 + timeline 兜底。

## 七、"不影响原站"兼容清单（逐项核验）

- 现有 `/api/create-order`（V1）、`/api/create-order-v2` 请求/响应体**一字不改**；小程序走新 `/api/client/order/create` 复用其内部逻辑。
- 现有 `GET /api/my-orders`、`/api/order-detail`（公开）、改期/取消/退款接口契约不变；只给新归属校验**追加** `user_id` 分支，匿名路径 `user_device_id` 原样保留。
- 新列全 NULL/默认、新表不参与既有 JOIN；`status / payment_status / service_status` ENUM 值域与线上一致，**不新增不删除**（如需新状态只加在枚举末尾）。
- 商户/超管端查询全部按 `m_id`，`user_id` 不改变任何商户列表结果；Excel 导入单无 `user_id`，逻辑不变。
- `order_no` 计数表、V1 下单、上传相对路径均保持原行为。
- 代码引用新列前 `deploy.sh` 已先跑迁移（顺序不变：pull → install → **migrate** → build → reload）。

## 八、分阶段实施路线

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P0 基线加固** | 全量 `mysqldump` 备份 + 补基线迁移记录线上已裸改列（`orders.user_id` 等）+ Redis 连接降级封装 | 可回滚基线 |
| **P1 顾客域数据** | 迁移 035–039；`users` / 新表建好；小程序登录接口（真 `code2session`） | 顾客可登录 |
| **P2 订单能力** | 订单归属写入、`user_id` 组合索引、新增 client 订单/查单/时间线/支付流水接口、状态推进收敛打时间线 | 顾客可下单查单 |
| **P3 并发/缓存增强** | 幂等键、Redis 锁与限流（可降级）、可用时段缓存、`lock_expires_at` 清理任务 | 并发稳健 |
| **P4 图片增强** | `ASSET_BASE_URL`、统一 storage 出口、删图回收、缩略图/格式修正（仅新文件） | 图片可演进 |

- P1/P2 即可端到端演示小程序下单闭环；P3/P4 为纯增强，随时可独立上线。

## 九、验证与回滚

- 每阶段上线后回归现有 C/B 端主链路：浏览 → 下单 → 付定金 → 商户确认 → 结清 → 查单。
- 回滚 = `knex migrate:rollback` 逐批 + 代码回退；因全部 additive，回滚不丢历史数据。
